# Interactive Stage Cards for the nvMolKit + Nemotron Demo

**Date:** 2026-08-04  
**Status:** Approved design

## Objective

Make the notebook slightly more interactive and make Nemotron's bounded autonomy more visible without weakening the existing fixed workflow, allowing arbitrary code execution, or making a failed button action fail the notebook cell.

The audience will approve every stage and may override only schema-valid parameters. For every approved stage, the notebook will show both the validated Nemotron tool call and the actual nvMolKit Python invocation that the controller executes.

## Non-goals

- Do not add workflow branching, stage skipping, stage reordering, or arbitrary tools.
- Do not expose raw JSON, a Python editor, or free-form parameter entry.
- Do not add a web application, database, checkpoint store, rollback system, or new agent framework.
- Do not expose hidden model reasoning. Show only a concise scientific decision summary.
- Do not replace the existing scientific executors or fixed workflow state machine.

## Architecture

Add a small `InteractiveWorkflow` layer around the existing controller. The existing synchronous `run_workflow(...)` path remains available for noninteractive execution and tests. The notebook uses one public `launch_interactive_workflow(...)` call.

The interactive layer owns presentation and approval state only. The existing controller continues to own:

- the exact six-stage dependency order;
- the allow-listed tool expected in each phase;
- strict Pydantic argument validation;
- the stateful Nemotron conversation;
- scientific execution and state transitions;
- structured result construction; and
- final synthesis validation.

`ipywidgets` will be a pinned project dependency. The notebook cell creates the interface and returns normally; later button actions run in guarded callbacks.

## Fixed Workflow

The stage order remains:

1. `inspect_library`
2. `generate_morgan_fingerprints`
3. `measure_tanimoto_similarity`
4. `discover_fused_butina_clusters`
5. `embed_representative_conformers`
6. `optimize_conformers_mmff94`

Nemotron proposes exactly the expected call at every stage. It may select only the parameters already represented by the strict schemas:

- fingerprint radius and size;
- clustering cutoff; and
- representative count, representative policy, and conformers per representative.

Parameter-free stages expose approval but no artificial controls.

The controls are fixed as follows:

| Stage | Editable controls |
| --- | --- |
| `inspect_library` | None |
| `generate_morgan_fingerprints` | Radius dropdown: 2 or 3; size dropdown: 1024 or 2048 |
| `measure_tanimoto_similarity` | None |
| `discover_fused_butina_clusters` | Cutoff slider: 0.40 through 0.60 in 0.05 increments |
| `embed_representative_conformers` | Representative-count slider: 3 through 6; policy dropdown with the two existing policies; conformer-count slider: 3 through 8 |
| `optimize_conformers_mmff94` | None |

## Interaction Model

The notebook displays one active stage card at a time. A card contains:

1. a compact summary of the evidence available from completed stages;
2. Nemotron's concise decision summary;
3. the proposed validated tool call;
4. dropdowns or bounded sliders initialized to the proposed values; and
5. an **Approve & Run** button.

Controls must encode the schema rather than accept free text. Literal choices use dropdowns or discrete selection controls. Numeric ranges use bounded sliders with steps that preserve the existing accepted domain.

When the user changes a value, the active preview updates. Approval validates the edited arguments again before execution. The transcript records both the proposal and the approved value when they differ.

After successful execution, the card becomes immutable, its figures appear immediately below it, and the next stage card opens automatically. Completed stages cannot be edited or rerun.

## Command Display

Every completed card shows two distinct code blocks:

1. **Validated Nemotron tool call** — the exact allow-listed call and approved arguments at the controller boundary.
2. **Scientific invocation executed by Python** — the corresponding library call used by the executor. This is the nvMolKit invocation for the five GPU stages and the supporting RDKit parsing invocation for `inspect_library`.

For example:

```python
# Validated Nemotron tool call
generate_morgan_fingerprints(radius=2, size=1024)
```

```python
# nvMolKit operation executed by Python
generator = MorganFingerprintGenerator(radius=2, fpSize=1024)
fingerprints = generator.GetFingerprints(molecules)
```

These strings must be generated by deterministic templates from the same validated argument object passed to the executor. They must not be free-form code written by Nemotron. Tests must tie every template to its executor so the displayed invocation cannot silently diverge from what ran. The UI label must say **nvMolKit invocation executed by Python** for GPU stages and **RDKit inspection executed by Python** for the input-inspection stage.

For calls that include local runtime objects, the display uses stable symbolic names such as `molecules` and `fingerprints`; it must not dump tensors, coordinates, credentials, or object representations.

## Stateful Agent Behavior

The same Nemotron conversation persists across the workflow. Each new proposal is requested only after the preceding structured scientific result has been appended to that conversation.

If the user accepts Nemotron's proposal, the approved call is executed unchanged. If the user overrides a parameter, the controller sends the executed values and an explicit `user_override` indication back with the structured tool result. Subsequent agent decisions therefore reflect what actually ran rather than what was originally proposed.

This provides bounded autonomy: Nemotron makes evidence-dependent scientific choices, while the human supervises each action and the controller retains authority over safety and reproducibility.

## State Transitions and Error Handling

Each stage follows this sequence:

1. Request the expected proposal from Nemotron.
2. Validate it with the existing Pydantic model.
3. Build controls from the validated values and schema.
4. Accept only a user approval or schema-valid parameter override.
5. Validate the approved arguments again.
6. Generate the two command displays from those exact arguments.
7. Invoke the existing scientific executor once.
8. Advance state only after a valid stage result is returned.
9. Append the executed arguments, override status, and compact result to the same Nemotron conversation.

The interface must guard its callbacks:

- Disable the active controls and button while work is running.
- Ignore duplicate clicks so a stage executes at most once.
- Catch callback exceptions and render a sanitized error inside the active card instead of raising a failed-cell traceback.
- On a hosted-model failure, remain at the same stage and offer **Retry Proposal**.
- On a scientific-execution failure, remain at the same stage and offer **Retry Execution** with the already approved arguments.
- On an invalid internal state or validation invariant, stop the workflow without a continue-anyway path.
- Request the final synthesis only after all six stages have completed exactly once.

A kernel restart restarts the demonstration from Preflight. Persisted sessions and recovery checkpoints are outside scope.

## Notebook Presentation

Retain the notebook's compact narrative:

- introduction;
- Preflight;
- user request;
- interactive agent run; and
- scientific boundary.

The interactive run remains one visible notebook cell. The user request and vendored nvMolKit skill continue to be passed explicitly. The resulting transcript follows a consistent visual cadence:

> evidence -> Nemotron decision -> proposed call -> human approval -> validated call -> scientific invocation -> result and figure

The final integrated synthesis appears after the last completed stage. It remains clearly labeled as schema-checked but not automatically fact-verified qualitative interpretation.

## Verification

Automated tests will verify:

- proposed values initialize the appropriate controls;
- controls expose only schema-valid values;
- overrides replace proposed values before execution;
- displayed calls derive from the exact approved argument object;
- each stage executes no more than once;
- duplicate clicks are ignored;
- failed proposals and executions remain at the current stage;
- executed values and override status return to the same Nemotron session;
- later stages cannot open early;
- final synthesis starts only after six successful stages;
- the existing synchronous controller and chemistry tests still pass; and
- the notebook is structurally valid and exposes one public interactive launch call.

The GPU acceptance path will exercise the interactive controller beneath the widget presentation with programmatic approvals. A manual Brev acceptance run will verify that JupyterLab renders the controls, stage buttons respond, both command blocks remain visible, figures appear, retries remain in place after a forced safe failure, and the final synthesis is displayed.

## Acceptance Criteria

The change is complete when a presenter can run Preflight, launch the interface, approve or safely override every stage, see the exact validated tool call and corresponding scientific invocation, observe every result and figure, and receive the final synthesis without any button-handler failure marking the notebook cell as failed. The transcript must distinguish the RDKit inspection from the five GPU-accelerated nvMolKit stages.
